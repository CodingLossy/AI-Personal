# ADR 0016 · 邮件:账户、同步、缓存、发送与会话级污染

- 状态:提议(M3 PR 1,业主已在 2026-11-05 确定 M3 方案第 5 节的全部问题)
- 日期:2026-11-05
- 相关:开发计划第 7 节(安全模型)、第 8 节 M3;`docs/milestones/M3-plan.md`;ADR 0003(条目索引)、ADR 0006(密钥引用)、ADR 0007(记忆 v2)、ADR 0010(工具框架与审批)、ADR 0012(条目 API)、ADR 0015(知识库)
- 修订:ADR 0010 第 4 节(条件预授权的污染判断改为按会话,见第 7 节)

## 背景

M3 让助手能读邮件、总结、起草回复,并在用户确认后发送。邮件是外部的、不可信的内容,所以首要的安全目标是:邮件里写的指令不能让助手发信或做其他有副作用的事。本 ADR 定下 M3 各 PR 共用的契约;实现细节(依赖版本、迁移 0009 的列)在 PR 2 起各自补充到本 ADR。

M2 的「读过不可信内容」标记只在一次运行(一轮)内有效:上一轮读过的邮件仍在模型上下文里,下一轮却不再算数。邮件让这个漏洞变得现实,所以本 ADR 一并修正。

## 决定

### 1. 账户配置与凭据

- 一个账户包含 IMAP(读取)与 SMTP(发送)两组服务器配置:主机、端口、加密方式(`tls` 直连 TLS,或 `starttls`),以及登录用户名与发件地址。
- **密码只保存引用**:`env:NAME` 读环境变量,`file:NAME` 读数据目录 `secrets.yaml` 中的键,规则与模型配置档的 `apiKeyRef` 相同(ADR 0006 第 2 节;`MailSecretRef` 复用同一正则)。API 与 Web UI 不接收明文密码;响应里只返回引用本身和 `passwordStatus`(`present` / `missing`)。
- **不支持明文连接**:加密方式只有 `tls` 与 `starttls`(业主决定 1:只支持应用专用密码 / 授权码,不做 OAuth)。本机测试用的模拟服务器在 PR 2 中用测试证书。
- 账户只能由用户经 API / UI 增删改,没有对应的工具,模型不能修改。
- `appendToSent`(默认 `true`):发送成功后是否把邮件 APPEND 到服务器的「已发送」(第 6 节)。Gmail 经 SMTP 发送时会自动保存,所以设置页的 Gmail 预设为 `false`。

### 2. 同步

- **文件夹**:只同步 special-use 为 `\Inbox` 与 `\Sent` 的文件夹;服务器不报告 special-use 时,收件箱用 `INBOX`,已发送按常见名称兜底(`Sent`、`Sent Messages`、`已发送` 等)。其他文件夹推迟。
- **新邮件**:按文件夹记录 `UIDVALIDITY` 与已同步的最大 UID,下一次只拉 `UID > lastUid`。`UIDVALIDITY` 变化时清空并重建该文件夹的缓存。首次同步只拉最近 N 天(`initialSyncDays`,默认 30,1–365;业主决定 2),用 `SINCE` 搜索,不拉全量。
- **已读状态与删除**:只按 UID 拉新邮件看不到服务器上的变化,而「今天未读」依赖准确的已读状态。所以每次同步还要在同步窗口(本地已缓存的 UID 范围)内:
  - 服务器支持 CONDSTORE 时,用 `CHANGEDSINCE highestModseq` 只取有变化的 FLAGS,并记录新的 `highestModseq`;
  - 不支持时,取窗口内的 UID 列表与 FLAGS 全量比对;
  - 服务器上已不存在的 UID 从本地缓存删除。
- **本地的 `unread` 与服务器的 `\Seen` 一致**。AI-Personal 读取正文一律用 `BODY.PEEK[]`,不会把服务器上的邮件标为已读;M3 也不提供「标为已读」。
- **去重**:Gmail 的标签以文件夹形式出现,同一封邮件可能出现在多个文件夹。同一账户内按 `Message-ID` 只保存一份,记下它出现在哪些文件夹;没有 `Message-ID` 的邮件按「文件夹 + UID」保存。
- **调度**:定时拉取为主,默认每 5 分钟(`syncIntervalMinutes`,5–1,440);IDLE 不做(业主决定 3)。每个账户一把锁,定时同步与手动同步不会同时进行;全局并发 1;失败按指数退避重试;网络断开不影响服务运行。不保持长连接:每次同步完断开 IMAP 连接,空闲时不占内存与连接。
- **兼容性**:登录后发送 IMAP `ID` 命令(163 邮箱要求,否则拒绝登录并提示 Unsafe Login)。GBK、GB18030、Big5 等编码由解析库处理;解析失败的部分保留原文并标记,不中断同步。
- **对服务器的写操作只有一种**:发送成功后 APPEND 到「已发送」(第 6 节)。标签、归档、删除、移动、标为已读都推迟。

### 3. 本地缓存

- 保存邮件头(发件人、收件人、抄送、主题、日期、`Message-ID`、`In-Reply-To`、`References`)、纯文本正文(HTML 邮件转成纯文本,不做富渲染),以及附件索引(文件名、类型、大小)。
- **附件内容只在用户要求时下载**(PR 4 的「加入知识库」);不自动入库。
- **全文检索**:正文进入单独的 `mail_fts`(trigram,与 `kb_chunks_fts` 相同做法)。PR 4 的 `mail` 条目只把主题与摘要放进 `items_fts`,同一段正文不索引两次。
- **向量**:邮件正文不进向量检索。只有用户加入知识库的附件会有分块与向量;删除账户时一并清理。

### 4. 会话串

- 优先用 `References` / `In-Reply-To`:一封邮件与它引用的邮件属于同一会话串。
- 都没有时,退回按「规范化主题 + 参与者集合」聚合:主题去掉 `Re:` / `Fwd:` / `回复:` / `转发:` 等前缀(大小写与全半角不敏感)并压缩空白,参与者为发件人与收件人地址的小写集合。
- 会话串的键(`threadKey`)由服务器计算,客户端只读。

### 5. 不可信内容

- 邮件头、正文、附件内容,以及 `mail.summarize` 根据它们生成的摘要,一律是不可信数据。交给模型时用 ADR 0010 第 7 节的 `UntrustedContent` 包装(`source.kind = 'email'`,已在契约中);所有 `mail.*` 读取类工具都声明 `untrustedOutput`。
- 显示名(`MailAddress.name`)、主题等字段在 UI 中一律按纯文本显示。

### 6. 草稿与发送

- `mail.draft`(`write`):只在本地保存草稿,不会自动发送。回复时由 core 根据 `replyToMessageId` 设置 `In-Reply-To` 与 `References`,不由模型提供。
- **草稿附件只能来自两处**:被回复邮件的附件(`kind: 'mail'`),或授权目录中的文件(`kind: 'file'`,按 `fs.read` 的路径规则校验)。其他来源返回 400。
- `mail.send`(`external`):**只接受 `draftId`**(业主决定 4),发送的就是保存着的那份草稿,模型不能在发送时改动内容。每次审批,不可预授权(ADR 0010 第 3 节:`external` 不能预授权,`remember` 返回 400)。审批卡片展示发件账户、收件人、抄送、主题、正文与附件名。
- 草稿在审批等待期间被修改时,原审批作废(按拒绝处理,`reason: 'cancelled'`),需要重新发起,确保用户批准的内容就是发出的内容。
- 发送成功后,`appendToSent` 为 `true` 时 APPEND 到「已发送」并标 `\Seen`;APPEND 失败不影响发送结果,只记录错误。每次发送都写审计(不含正文)。

### 7. 会话级污染(修订 ADR 0010 第 4 节)

- 会话中只要有一次工具返回了不可信内容(`untrustedOutput`),该会话就**一直**视为「读过不可信内容」,不只是当前一轮。这个状态记录在会话上(迁移 0009),重启后仍然有效;被 fork 的会话继承它。
- 以一封邮件为上下文新建的会话(PR 4 的「问 AI」)从一开始就视为读过不可信内容。
- 影响:
  - **条件预授权全部失效**,包括 M2 的 `memory.write`(业主决定 8,修改 M2 的现有行为):会话被污染后,`memory.write` 一定需要审批;自动抽取的结果只进隔离区(ADR 0007 第 5.5 节)。
  - **收件人检查**:会话被污染后,`mail.send` 的每个收件人与抄送都必须满足以下之一,否则审批请求带 `recipient_untrusted` 警告(第 8 节),卡片标红:
    - 地址出现在用户本人在该会话中发的消息里(只看主人的直接消息,不看工具结果);
    - 是被回复邮件的发件人或 `Reply-To`。
  - 判断由 core 用已知事实完成,不由模型给出。
- 已保存的预授权(如 `fs.write` 按目录的预授权)不受污染影响,仍然有效。这是业主事先明确授权的范围,但意味着邮件中的指令在理论上可以诱导模型在该目录内写文件;评测集覆盖这种情况,文档提示用户谨慎设置 `always` 预授权。

### 8. 审批警告(`packages/shared`,本 PR)

- 新类型 `ApprovalWarning`:`{ code: string, message: string }`。`code` 是字符串而不是枚举,以后新增警告不会成为破坏性修改;已知的值由 `ApprovalWarningCode` 列出,M3 只有 `recipient_untrusted`。
- `approval-required` 事件与 `ApprovalRequest` 增加可选字段 `warnings: ApprovalWarning[]`;旧服务器不发送,旧客户端忽略即可。`message` 由 core 生成,不含模型或邮件提供的文字。
- Web 审批卡片有警告时整体标红并逐条显示。

### 9. 记忆

- 邮件内容不能直接成为记忆(开发计划第 7 节「记忆安全」):只能由模型提议,经用户确认后写入。会话级污染(第 7 节)保证读过邮件的会话里 `memory.write` 一定需要审批。

### 10. 契约(`packages/shared`,本 PR)

均为新增的类型或可选字段,不修改已有接口:

- `MailSecretRef`、`MailSecurity`、`MailServer`。
- `MailAccount`(响应)、`MailAccountInput`(新建)、`MailAccountPatch`(部分更新),含 `appendToSent`。
- `MailFolder`:账户内的文件夹,含 `specialUse`、`uidValidity`、`lastUid`、`highestModseq`、`lastSyncedAt`。
- `MailAddress`、`MailAttachment`(只有索引)、`MailMessage`(含 `threadKey`、`inReplyTo`、`references`、`unread`、纯文本 `text`)。
- `MailThread`:会话串的摘要(主题、参与者、条数、未读数、最后一封的时间)。
- `MailDraftAttachment`、`MailDraft` / `MailDraftInput`:本地草稿,`replyToMessageId` 可选。
- `MailSendInput`:只有 `draftId`,未知字段一律拒绝。
- `ApprovalWarning`、`ApprovalWarningCode`;`approval-required` 事件与 `ApprovalRequest` 的可选 `warnings`。
- `ItemSource`:列出已知的 `items.source`(`files`、`novels`、`sessions`、`memory`、`mail`)。`Item.source` 仍是字符串。

REST 路径与其他工具的输入输出 schema 随 PR 2、PR 3 增加。联系人与「人物」不在 M3(业主决定 6,推迟到 M5)。

### 11. 实现(M3 PR 2 `feat/mail-sync`)

- **依赖**:`imapflow`(MIT)、`mailparser`(MIT)、`nodemailer`(MIT-0),都在新包 `packages/mail` 中。三者 import 后约占 35 MiB RSS(本机实测),所以只在**子进程**中加载:每次同步或连接测试 `fork` 一个 Node 进程(堆上限 192 MiB、5 分钟超时),结果经 IPC 交回服务器后退出。密码经 IPC 传入,不放在命令行或环境变量里;子进程只继承 `PATH`、`TEMP` 等运行所需的环境变量。
- **不用 worker_threads**:实测 worker 退出后,它用过的内存大多仍算在主进程的 RSS 里(每次同步后约多 60 MiB,并缓慢增长);子进程退出后主进程 RSS 不变(本机 57 MiB → 57 MiB)。代价是每次同步多约 50 ms 的进程启动时间,对 5 分钟一次的拉取可以忽略。
- **主进程只写数据库**:子进程返回每个文件夹的新邮件、已读变化、删除的 UID 与新的 `UIDVALIDITY` / `HIGHESTMODSEQ`;服务器在一个事务里写入(`packages/storage` 的 `mail.applySync`),仍然只有 storage 打开数据库。
- **批量**:每个文件夹每次最多拉 200 封新邮件;还有剩余时 30 秒后自动继续。每封只取前 1 MiB 原文解析正文(`BODY.PEEK[]<0.1048576>`),附件索引来自 BODYSTRUCTURE,大附件不会被下载。
- **调度**:每分钟检查到期的账户(`next_sync_at`),全局串行;同一账户同时触发的同步共用一次结果。失败按 `间隔 × 2^(失败次数-1)` 退避,最长 6 小时;修改账户配置会清除退避。
- **会话串**:`threadKey` 先由引用链或主题算出;写入时如果找到已缓存的相关邮件(被引用的原邮件,或先到的回复),沿用它们的键。
- **REST**:`GET /mail/presets`、`/mail/accounts` 增删改查、`GET /mail/accounts/{id}/folders`、`POST /mail/accounts/{id}/test`(分别测 IMAP 与 SMTP 登录,不发信)、`POST /mail/accounts/{id}/sync`。错误说明由子进程归类为人能看懂的文字,服务器再经脱敏器处理一次。
- **迁移 0009**:`mail_accounts`、`mail_folders`、`mail_messages`(整数主键 `seq` 作为 `mail_fts` 的 rowid)、`mail_message_folders`、`mail_attachments`、`mail_drafts`、`mail_fts`;`sessions.untrusted_at`(PR 3 起使用)。

### 12. 实现(M3 PR 3 `feat/mail-tools`)

- **工具**(`packages/mail/src/tools.ts`,在服务器的组合根中注册):
  - `mail.list`(可按账户、收件箱 / 已发送、未读、`today` 过滤)、`mail.search`(`mail_fts`)、`mail.read`(正文最多 20,000 字)、`mail.summarize`(一封、整个会话串或「今天未读」,用 cheap 配置档,输入最多 30,000 字):都是 `read`、`untrustedOutput`,输出包成 `UntrustedContent`(`source.kind = 'email'`),摘要同样算不可信内容。「今天」按服务器时区(容器的 `TZ`)计算。
  - `mail.draft`(`write`):只存本地。回复时由 core 根据被回复邮件设置 `In-Reply-To` / `References`。附件来源按第 6 节校验:`kind: 'mail'` 必须是被回复邮件自己的附件;`kind: 'file'` 用 `fs.*` 的 `resolveInRoots` 校验(授权目录外的路径按越权拒绝并审计),发送前按当时的授权目录再校验一次。
  - `mail.send`(`external`,不可预授权):输入只有 `draftId`(`MailSendInput`,其他字段一律拒绝)。审批卡片的说明由 core 从草稿生成:发件账户、收件人、抄送、主题、附件名与大小、正文(超过 4,000 字截断)。发送在邮件子进程中完成:组装原文 → SMTP 发出 → `appendToSent` 时 APPEND 到「已发送」并标 `\Seen`(APPEND 失败只在结果中说明)。发送后删除草稿。
- **审批时间**:`ToolContext.approvalRequestedAt` 由 core 在审批后执行时提供;草稿的 `updatedAt` 晚于它时 `mail.send` 拒绝执行。
- **会话级污染**:`RunManager` 每轮开始时读取 `sessions.untrusted_at`,有工具返回不可信内容时写入;`sessions.create(..., { untrusted: true })` 供 PR 4 的「问 AI」使用。目前还没有会话 fork 的实现,fork 时继承污染状态的规则在实现 fork 时落实。
- **审批警告**:`ToolDefinition.warnings(input, context)` 由 core 在创建审批请求时调用;迁移 0010 给 `approval_requests` 加 `warnings_json`,`approval-required` 事件与 `GET /approvals` 都带 `warnings`。`recipient_untrusted` 的允许集合:本会话中主人消息原文里出现的地址(不区分大小写),以及被回复邮件的发件人与 `Reply-To`。Web 的审批卡片有警告时红框显示。
- **系统提示**:不可信内容的说明从「网页」扩展为「网页、文件与邮件」。
- **评测**:`apps/server/src/mail-injection.eval.test.ts`(14 条,`pnpm eval` 一并运行)。脚本化的模型假定已被邮件内容完全操纵,评测检查 core 的防线;把会话级污染改回按轮判断时,其中 3 条会失败(本机验证过)。

## 后果

- 账户配置与模型配置档用同一套密钥引用;代价是用户要先把授权码放进环境变量或 `secrets.yaml`。
- 只支持 TLS / STARTTLS,极少数只提供明文 IMAP 的服务器无法接入。
- FLAGS 重新同步让「未读」与服务器一致,代价是不支持 CONDSTORE 的服务器每次同步要多取一次窗口内的 FLAGS(30 天通常是几百到几千封,只取 UID 与 FLAGS)。
- 只从草稿发送让审批卡片展示的就是实际发出的内容,代价是每次发送要多一步起草。
- 会话级污染比 M2 更严:读过网页、文件或邮件的会话中,之后的 `memory.write` 都要审批。用户想无审批地写记忆,可以新开一个会话。
- 只有 APPEND 到「已发送」会写服务器;用户在别的客户端看到的已读状态不会因为 AI-Personal 改变。
